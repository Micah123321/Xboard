# 全天访问流量查询与请求超时优化（2026-10-22）

访问流量列表默认最近24小时。原前端15秒超时会提前取消请求；pageSize=20仍需统计完整筛选范围和全部分组。用户已授权生产只读诊断与性能对照，后续接受十几秒查询并要求延长前端等待时间。

## 最终行为

- 访问流量列表与CSV/HTML导出请求设置 timeout=60000（60秒）。管理端类型检查与独立生产构建通过，产物在 output/access-query-2026-10-22/admin。未发布到线上。
- 后端一次完整分组扫描同时计算原始/已知计费汇总、分类、总分组数和排名；用有界优先队列保留当前页所需排名，避免另做一次全量汇总及宽结果窗口排序。前10000名使用此路径，更深分页保留数据库分页方式，限制堆内存。
- 完整分组键保留，分类比较仍由SQL按原数据库collation执行。每组未完全结算时列表计费仍为NULL，但已结算部分仍计入汇总；混合倍率、零字节类别、历史节点名、邮箱和全量导出口径保持一致。
- 选出当前页后才关联展示资料，报告统计用首条匹配明细存在性判断，报告跨多个类别只计一次。正常请求为4条数据查询；独立MySQL请求另有事务隔离设置及事务控制。
- MySQL无用户/节点/类别限制时，由报告采集时间索引先关联明细report_id索引，避免优化器选择扫描全部历史明细；有这些筛选时保留其索引选择。无需新增迁移。

时间边界依据接收端从首版即存在的不变量 last_seen <= observed_at + 300：last_seen>=start 可推出报告 observed_at>=start-300。新增报告下界保留等号，不对 observed_at 或 bucket_at增加结束上界，延迟报告和历史长片段仍按原重叠条件计入。外部直接写库且违反接收契约的数据不能依赖此不变量；本轮同快照生产完整响应已核对一致。

## 生产只读证据

2026-10-22，北京时间22:09起，现有生产MySQL8.0.25和web容器，单条SQL限12秒，READ ONLY事务；未修改业务数据、索引或服务文件，候选类仅在单次PHP进程内加载。

- 数据库估算约746万条明细，数据3.80GB、索引3.18GB。原EXPLAIN显示明细access_type=ALL，尽管已有时间区间索引。原汇总约7.1秒，列表在12秒限时中断；完整当前部署接口约19.3秒仍失败。
- 最终候选两次近24小时完整调用13.482秒、14.050秒，均返回20行。此为服务层实测，未包含公网HTTP与浏览器时间，不能保证每次在旧15秒前返回，因此前端按用户要求改为60秒。
- 同一快照用原查询口径的非窗口分页与独立分组计数作完整结果校验：旧口径22.455秒，候选14.050秒，减少约37.43%。两者均为59034组、268538805554原始字节，整份规范化响应SHA256相同：a9df36295994911b5874204e6f1d1e84fceb934ed0182ddcc47e5fbeedbc9d48。该旧口径对照为避免窗口SQL中断而关闭窗口、独立计数，并调整物理关联顺序；不是声称原部署接口成功耗时22.455秒。
- 独立流式分组实验约40MB峰值内存，PHP进程上限256MB；PDO仍可能缓冲整个数值分组结果，堆只限制排名保留量，不代表任何数据规模都能固定内存。

第一版仅在SQLite快约26%的方案在生产仍超时，因此未采用该本地数字作为线上结论。试验过时间索引、共享CTE与分区等只读方案，最终交付以上流式路径。

原始证据保存在 output/access-query-2026-10-22/production-inspect.json、production-compare-streamed.json、production-oracle-compare.json。包括计划与匿名摘要，不导出域名、账户邮箱及访问明细。部分SSH握手失败发生在命令执行前；一次后台仅返回通用失败，随后用同步调用取得SQL限时证据，未宣称失败任务成功。
